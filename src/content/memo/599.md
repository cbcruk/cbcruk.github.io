**언제** — 브라우저가 `CORS error` 를 띄웠을 때. **CORS 설정을 뒤지기 전에** 이 표로 갈래부터 정한다.

| preflight | `server` | ACAO | 갈래 | 실제 원인 |
|---|---|---|---|---|
| `503` | `awselb/2.0` | 없음 | **인프라** | 타깃 그룹에 healthy target 0 — 서비스 다운·배포 실패·CrashLoop |
| `502` | `awselb/2.0` | 없음 | **인프라** | 타깃이 커넥션을 끊거나 잘못된 응답 — 앱 크래시·OOM·포트 불일치 |
| `504` | `awselb/2.0` | 없음 | **인프라** | LB idle timeout 초과 — 느린 쿼리·외부 연동 지연 |
| `404` | 앱 | 없음 | **경로** | 앱까지 갔지만 경로가 없음 — path 오타, ingress rule 불일치 |
| `204`·`200` | 앱 | 없음 | **CORS** | 앱이 응답했는데 헤더가 없다 = 진짜 CORS 미설정 |
| `204` | 앱 | 있음 | **CORS** | `access-control-allow-headers` 에 요청 헤더가 빠짐 |
| `204` | 앱 | `*` | **CORS** | 쿠키·`credentials: 'include'` 와 `*` 는 **병용 불가** — 오리진 명시 + `credentials: true` |
| `204` | 앱 | 정상 | **정상** | CORS 문제 아님. 본 요청의 본문·인증·에러를 본다 |

**`server` 가 로드밸런서면 CORS 설정을 뒤지는 시간은 전부 낭비다** — 애플리케이션은 그 요청을 받은 적이 없다.

## 왜 CORS 로 오진하게 되나

preflight 응답에 `Access-Control-Allow-Origin` 이 **없기만 하면** 브라우저는 원인을 구분하지 않고 전부 CORS 에러로 뭉갠다. 5xx·404·타임아웃이 다 여기 해당한다.

```text
정상  브라우저 ──OPTIONS──> LB ──전달──> 앱(healthy)
                                          └─ 204 + access-control-allow-origin ─> 브라우저

장애  브라우저 ──OPTIONS──> LB ──X──> 앱(healthy 0)
                             └─ 503, CORS 헤더 없음 (LB 가 직접 생성) ─> 브라우저
                                                        → 브라우저: "CORS error"
```

차이는 **응답을 만든 주체** 하나다. LB 가 타깃에 닿기 전에 스스로 5xx 를 만들면 그 응답은 앱을 거치지 않으므로 CORS 헤더가 있을 수 없다. 브라우저에게 두 경우의 결론은 똑같다 — "허용 헤더가 없다". **서버가 죽었다는 정보는 어디에도 나타나지 않는다.**

`content-type: application/json` 이나 `authorization` 을 쓰는 요청은 simple request 가 아니라서 본 요청 앞에 `OPTIONS` 가 먼저 나간다는 게 전제다.

## R1. preflight 를 직접 쏜다

> **"Copy as cURL" 로 뜬 본 요청을 재현하지 말 것.** 그건 POST 고, 실패한 건 그 앞의 preflight 다. **인증 정보도 넣지 않는다** — preflight 판별에 자격증명은 필요 없다.

```bash
curl -s -o /dev/null -D - -X OPTIONS \
  'https://api.example.com/graphql' \
  -H 'Origin: https://app.example.com' \
  -H 'Access-Control-Request-Method: POST' \
  -H 'Access-Control-Request-Headers: content-type,authorization'
```

**확인** — status code 와 `server` 헤더를 위 표에 대조한다. DevTools 보다 curl 이 빠른 이유는 **curl 이 CORS 를 적용하지 않아서** 서버가 실제로 보낸 것을 그대로 보여주기 때문이다. Network 탭은 실패한 preflight 를 `(failed) net::ERR_FAILED` 나 `CORS error` 로만 표시하고 Console 도 `No 'Access-Control-Allow-Origin' header is present` 로 동일해서, status 를 보려면 `OPTIONS` row 를 직접 열어야 하고 차단된 경우엔 그마저 비어 보인다.

## R2. 형제 호스트와 대조한다

같은 경로를 형제 호스트에 던진다. **한 호스트만 죽었으면 배포·타깃 그룹 문제고, 전부 같으면 코드·설정 문제다.**

```bash
for h in api-a api-b api-c; do
  printf '%-6s ' "$h"
  curl -s -o /dev/null -w '%{http_code}\n' \
    "https://$h.example.com/graphql" \
    -X OPTIONS -H 'Origin: https://app.example.com' \
    -H 'Access-Control-Request-Method: POST'
done
```

실제 장애에서는 셋 중 하나만 `/health`·`/`·`/graphql` **모든 경로**가 503 이었다 — 타깃 그룹에 healthy target 이 없다는 뜻이다. 응답 둘을 나란히 놓으면 갈래가 바로 보인다:

```http
HTTP/2 503
server: awselb/2.0
content-type: text/html
← access-control-* 헤더가 하나도 없다
```

```http
HTTP/2 204
x-powered-by: Express
access-control-allow-origin: *
access-control-allow-methods: GET,HEAD,PUT,PATCH,POST,DELETE
access-control-allow-headers: content-type,authorization
```

즉시 우회는 프론트가 부르는 호스트를 살아 있는 쪽으로 돌리는 것이고, 근본 조치는 죽은 타깃을 되살리는 것이다.

## R3. 503 을 고쳐도 CORS 가 남는지 본다

**엔드포인트를 쪼개 배포하면 CORS 설정이 한 곳만 빠질 수 있다.** 이번 장애에서 살아 있던 호스트들은 `enableCors()` 를 가진 통합 앱이었고, 죽은 호스트가 가리키는 분리 배포 bootstrap 에는 그게 **없었다** — 브라우저를 상대하는 여섯 중 하나만 빠져 있었고, `git log -S 'enableCors'` 가 비어 있어 지운 게 아니라 처음부터 없던 것이었다. 503 이 해소되면 그때 CORS 에러가 진짜로 나타난다.

**함정 — 죽은 설정이 있으면 있다고 착각한다.** 설정 파일에 `cors.enabled`·`methods`·`domain` 이 정의돼 있는데 **그걸 읽는 코드가 0건**이었다. 소켓 어댑터의 `corsOrigins` 파라미터도 생성자 본문·호출부 양쪽에서 미사용이었다. 오리진 화이트리스트를 도입할 계획이 없으면 지우고, 있으면 실제로 연결한다. `enableCors()` 를 인자 없이 부르면 `cors` 패키지 기본값(`*`, `GET,HEAD,PUT,PATCH,POST,DELETE`, `credentials` 미설정)이다.

## 재발 방지

| 담당 | 조치 |
|---|---|
| 프론트 | Console 메시지를 그대로 믿지 않는다. `OPTIONS` row 의 status 를 열어 보고, 애매하면 `R1` |
| 백엔드 | 브라우저를 상대하는 bootstrap 끼리 CORS 설정을 맞춘다. `*` 로 통일할지 화이트리스트로 갈지는 별도 결정 |
| 인프라 | **LB 5xx 는 앱이 헤더를 붙일 방법 자체가 없다.** 타깃 unhealthy 알림이 프론트 에러 리포트보다 먼저 울려야 한다 |
| 보안 | 재현 요청에 자격증명을 넣지 않는다. 넣어 공유했다면 개발 환경이라도 교체한다 |
