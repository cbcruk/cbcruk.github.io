> 이 4부로 구성된 블로그 시리즈에서는 Chrome 브라우저의 내부 구조를 간략히 살펴본 후 렌더링 파이프라인의 세부사항을 살펴봅니다. 브라우저가 코드를 작동하는 웹사이트로 변환하는 방법을 궁금해하거나 성능 개선을 위해 특정 기법이 제안되는 이유를 잘 모르겠다면 이 시리즈가 도움이 될 것입니다.

[^138-1]: 구조 — CPU·GPU·프로세스·스레드에서 출발해 Chrome 의 멀티 프로세스 구조(브라우저·렌더러·GPU 등 무엇이 무엇을 맡나), 그 이점과 메모리 절충(서비스화), 프레임마다 렌더러를 나누는 사이트 격리.
[^138-2]: 탐색 — 주소를 치면 브라우저 프로세스가 요청을 시작해 렌더러에 넘기기까지. 다른 사이트로 갈 때와 서비스 워커가 끼어들 때, Navigation Preload.
[^138-3]: 렌더러 프로세스 안 — 파싱 → 스타일 계산 → 레이아웃 → 페인트 → 합성. 리소스 로딩 힌트도 여기서.
[^138-4]: 입력 — 입력 이벤트가 먼저 컴포지터에 오는 이유, non-fast scrollable 영역, 취소 가능한 이벤트 확인, 이벤트 타깃 찾기, 메인 스레드로 보내는 횟수 줄이기(`getCoalescedEvents`).
