**GenUI 는 화면의 일부를 모델 출력으로 정하는 것이다.** 모델이 **어떤 타입의 값을 내놓느냐**로 세 갈래가 갈린다 — 인자(`Args`) · 부품 트리(`Node`) · 코드(`String`). 타입이 좁을수록 검사가 많이 막아주고, `String` 이면 막을 게 없어 샌드박스만 남는다.

![Static 은 모델 → Args → 도메인 툴 → Result → render() → Node, Declarative 는 render() 자리만 모델로 바뀐다. Open-ended 는 모델 → String → 샌드박스로 계약도 타입 검사도 없다.](/svg/genui_three_modes_flow.svg)

Static 과 Declarative 는 **한 칸만 다르다** — `Result` 를 `Node` 로 바꾸는 자리에 우리 함수가 있느냐 모델이 있느냐. 그래서 Static 에서 "왜 이 화면이 나왔나"는 `render()` 를 읽으면 답이 나온다.

- **Static**: 입력이 자유 텍스트라서. 모델이 하는 일은 그걸 `Args` 로 바꾸는 것뿐이고 화면은 여전히 우리가 고른다.
- **Declarative**: 관심사 조합마다 화면을 미리 만들어 둘 수 없어서. 이때 GenUI 가 하는 일은 추상화를 올리는 게 아니라 **조합을 정하는 시점을 컴파일 타임에서 런타임으로 옮기는 것**이다.

타입으로 막던 규칙이 프롬프트 정책으로 옮겨가고, 조합 폭발은 사라지지 않고 카탈로그 유지보수로 간다.

1. 사용자 입력이 열거 가능한 선택지다 → GenUI 가 아니다. 필터 UI 가 답이다.
2. 자유 입력이지만 나올 화면 종류를 셀 수 있다 → **Static.** 대부분 여기서 끝난다.
3. 화면 구성이 데이터 양(0건/1건/N건)이 아니라 관심사 조합(날씨+일정, 예산+체크리스트)으로 달라진다 → **Declarative.**
4. 우리 부품으로는 표현이 안 되는 일회성 위젯 → 그 조각만 **Open-ended.** 페이지 전체는 아니다.

모델이 화면을 만든다고 해서 결정권이 모델로 가지는 않는다. **모델 출력을 받아주는 계약(그림의 회색 칸)을 쥔 쪽**으로 간다 — Declarative 라면 카탈로그를 소유한 팀이 사실상 UI 를 정한다.

| 계약으로 두는 것        | 주도하는 쪽   |
| ----------------------- | ------------- |
| 서버 스키마             | 백엔드        |
| 인텐트 + 결과 상태 집합 | 기획·도메인   |
| 컴포넌트 카탈로그       | 디자인 시스템 |
