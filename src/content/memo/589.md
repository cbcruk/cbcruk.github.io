**언제** — 함수 호출에서 `T` 가 엉뚱하게 정해졌을 때. 증상으로 찾아 들어간다.

| 증상                                  | 원인                                                      | 그림               |
| ------------------------------------- | --------------------------------------------------------- | ------------------ |
| 이상하게 `unknown` 이 나온다          | 그 변수가 바운드·조건 부분·인자에 안 드러난 위치에만 있다 | 모델, 기본값, 우회 |
| 형제 타입인데 첫 인자로 고정됐다      | 접기의 "첫 후보 유지"                                     | 해소               |
| 추론은 됐는데 그 값으로 체크가 깨진다 | 조건부 가지를 평가하지 않는다                             | 조건부             |
| union 인자에서만 실패한다             | 분배 후보가 재-union 되지 않는다                          | union, 해소        |

## 모델 — 추론은 딱 2단계다

![source 타입(인자 + 기대 반환)과 target 타입(매개변수 + 반환)을 ① 수집이 나란히 walk 하며, bare T 를 만나면 그 자리의 source 를 후보로 기록한다. 후보는 출력 위치면 공변 후보, 입력 위치면 반변 후보 리스트에 쌓인다. ② 해소가 리스트마다 하나로 접어 T 에 주입한다. ③ 일반 타입 체크는 그 뒤에야 따로 돈다 — 수집과 타입 체크는 별개 단계다. extends 바운드·기본값·조건부의 조건 부분·상위 타입은 후보가 되지 않는다. 후보는 source 와 그 구조적 부분에서만 줍는다.](/svg/ts_inference_two_stages.svg)

`Elephant<Savannah>` 에서 후보가 될 수 있는 건 `Elephant<Savannah>`·`Savannah` 뿐이고 상위 타입 `Animal`·`Location` 은 안 된다 — `number` 인자로 `string` 바인딩을 만들 방법은 없다.

## 수집

![f<A, B, C>(x: A, y: (a: B) => C) 에 f(true, (it: number) => 'hello') 를 넘기면 target 과 source 를 같은 자리끼리 맞춘다. x 자리의 A 는 true 를 받아 A = boolean, 함수 매개변수 자리의 B 는 number 를 받아 B = number, 반환 자리의 C 는 'hello' 를 받아 C = string. 함수 매개변수 자리만 반변이고 나머지는 공변이라 후보가 두 리스트에 나뉘어 쌓인다.](/svg/ts_infer_walk.svg)

**타입 별칭 안으로도 walk 한다.** `type ArrayContainer<T> = T[] | { array: T[] }` 에 `number[]` 를 매칭하면 배열 쪽이 맞아 `E = number`.

**조건부 — 조건은 안 보고 결과 가지에서 줍는다.**

```ts
type Pair<A, B> = A extends string ? Map<A, B> : [A, B]
function f<A, B>(x: Pair<A, B>) {}
f([1, 2]) // A = number, B = number
f(new Map([['a', 1]])) // A = string, B = number
f(['a', 'b']) // TS2345: string[] is not assignable to Map<string, string>
```

![type Pair<A, B> = A extends string ? Map<A, B> : [A, B] 에 f(['a', 'b']) 를 넘긴다. 수집은 조건을 평가하지 않고 두 결과 가지에 모두 맞춰 보며, 맞는 [A, B] 가지에서 A = string, B = string 을 줍는다. 체크는 정해진 A = string 으로 조건을 평가해 첫 번째 가지 Map<string, string> 으로 가고, string[] 은 거기에 대입할 수 없어 TS2345. f([1, 2]) 는 수집과 체크가 둘 다 [A, B] 가지라 통과한다.](/svg/ts_infer_conditional_branch.svg)

**`infer T` 는 새 타입변수를 만든다** — 조건 부분 중 유일한 예외. `Awaited<Promise<Promise<number>>>` 의 첫 전개 `U = Promise<number>` 와 재귀 전개 `U = number` 는 별개 변수다.

![source 가 union S1 | S2 이고 target 이 맨몸 T 가 아니면, 가지마다 따로 walk 해서 후보 c1, c2 를 얻는다. 두 후보는 같은 리스트에 쌓이지만 다시 union 되지 않는다. 그래서 해소 규칙이 리스트에서 하나를 고르고, 결과가 c1 | c2 가 아닐 수 있다 — union 인자에서만 실패하는 이유다.](/svg/ts_infer_union_distribute.svg)

**source 의 intersection** 은 그대로 두지만, 객체 타입(`{ x: T }`)에 구조적으로 맞춰야 할 때만 병합된 객체 형태가 생긴다.

## target intersection

```ts
function foo<A, B>(it: A & B) {}
foo(42) // A = unknown, B = unknown
function bar<A>(it: A & number) {}
bar(42 as number & { brand: 'USD' }) // A = { brand: "USD" }
```

![foo<A, B>(it: A & B) 에 42 를 넘기면 어느 쪽에 줄지 모호해서 아무것도 기록하지 않고 A, B 모두 unknown. A & 무언가 에서 A 를 떼어낼 때는 차집합이 아니라 포획 유용성을 최대화한다. A & { x: number } 에 { x: number, y: number } 를 넘기면 차집합이라면 { y: number } 겠지만 실제로는 전체 객체가 A 가 된다. A & number 에 number & { brand: 'USD' }, A & 'a' 에 'a' & { brand: 1 } 을 넘기면 나머지인 { brand: ... } 가 A 가 된다. intersection 순서는 무관하다.](/svg/ts_infer_target_intersection.svg)

## 해소

```ts
declare function f<T>(x: T, y: T): T
f(d, a) // Animal
f(d, c) // Dog
f('a', 1) // "a"
f('a', 'b') // "a"|"b"
```

![후보 리스트(공변 기준, 반변은 관계를 반대로 본다)에서 익명 객체·배열 리터럴이 여럿이면 먼저 union 한다(named 타입끼리는 안 한다). 그다음 ① 전부 같은 base 의 리터럴이면 union — f('a', 'b') 는 "a" | "b". ② 아니면 다른 모두의 strict 상위인 후보가 있으면 그것 — f(d, a) 는 Animal. ③ 없으면 왼쪽부터 접고, 상위가 리스트에 없으면 첫 후보 — f(d, c) 는 Dog, f('a', 1) 은 "a". 철칙: 결과는 리스트에 없는 타입이 될 수 없다. f(d, c) 는 공통 상위 Animal 도 Dog | Cat 도 아니다.](/svg/ts_infer_fold.svg)

![f<T>(x: T, sink: (t: T) => void) 에 f(new Dog(), (_: Animal) => {}) 를 넘기면 공변 결과 Dog 와 반변 결과 Animal 이 나온다. 공변 결과가 반변 결과의 하위 타입이면 더 정밀한 공변이 이긴다 — Dog 는 Animal 의 하위라 T = Dog. 아니면 기본은 반변이 이기고, 반변 결과가 바운드를 못 지키면 공변으로 폴백한다.](/svg/ts_infer_co_contra.svg)

![type Result<V, E = never> = { okay: V } | { error: E } 이고 function f<V, E>(x: Result<V, E>) 에 f({ okay: 42 }) 를 넘기면 E 자리에 온 값이 없어 후보가 비어 있다. 빈 리스트면 해소 대상인 f 의 E 에서 기본값을 찾는데 없으니 E = unknown. Result 의 never 기본값은 Result<X> 처럼 인자를 생략할 때만 쓰여서 여기서는 안 본다. never 를 원하면 function f<V, E = never> 로 선언한다. 해소값이 바운드를 못 지키면 바운드로 교체된다.](/svg/ts_infer_default.svg)

**우선순위 비트** — 후보마다 태그가 붙고, 더 높은 우선순위 후보가 오면 낮은 것들은 지워진다. `ReturnType`(함수를 인자로 넘길 때 반환 타입 추론), `LiteralKeyof`(리터럴을 `keyof T` 에 매칭), `MappedTypeConstraint` 셋은 상위/하위 대신 **union(공변)/intersection(반변)** 으로 해소한다.

## 우회

```ts
function foo(x: Exclude<unknown, number>) {}
function bar<X>(x: Exclude<X, number>) {}
function quz<X, Y extends Exclude<X, number>>(x: Y) {}
bar(42) // 에러: 42 not assignable to never
```

![제네릭 함수 안에서는 타입변수가 미확정이라 조건부를 평가할 수 없다. foo(x: Exclude<unknown, number>) 는 타입변수가 없어 바로 unknown 으로 줄어 foo(42) 를 못 막는다. bar<X>(x: Exclude<X, number>) 는 파라미터 위치에서 X = number 를 추론해 Exclude<number, number> = never 가 되고 bar(42) 가 에러 — 이것만 막는다. quz<X, Y extends Exclude<X, number>>(x: Y) 는 X 가 바운드에만 있어 추론되지 않고 unknown 이라 못 막는다.](/svg/ts_infer_exclude.svg)

**`NoInfer<T>`** — 그 위치에서 `T` 의 후보를 줍지 않는다. 다른 위치에서 정해진 `T` 를 강제할 때.

```ts
function foo<K, V, T extends Map<K, V>>(map: T, key: K): [T, V] {
  return [map, map.get(key)!]
}
foo(new Map([[42, '42']]), 42) // [Map<number,string>, unknown]

// 1) extractor 타입
type GetV<T extends Map<unknown, unknown>> = T extends Map<unknown, infer V> ? V : never
function foo<K, V, T extends Map<K, V>>(map: T, key: K): [T, GetV<T>] {
  return [map, map.get(key) as GetV<T>]
}

// 2) map: T & Map<K, V>
function foo<K, V, T extends Map<K, V>>(map: T & Map<K, V>, key: K): [T, V] { … }
```

![foo<K, V, T extends Map<K, V>>(map: T, key: K) 에 foo(new Map([[42, '42']]), 42) 를 넘기면 map 에서 T = Map<number, string>, key 에서 K = number 를 줍지만 V 는 바운드에만 있어 후보가 없고 unknown 이 된다. 해법은 둘이고 둘 다는 안 된다. extractor 타입 GetV<T> 로 T 에서 infer V 를 꺼내면 union 인자를 지원하지만 반환에 캐스트가 필요하다. map: T & Map<K, V> 로 V 를 매개변수 위치에 드러내면 캐스트가 필요 없지만 union 인자에서 깨진다.](/svg/ts_infer_map_v.svg)

**함정** — `A extends string ? { [key in A]: B } : …` 형태의 매핑드 타입에서는 키/값 추론이 안 된다. `[A, B]` 같은 구조로 쓴다. 그리고 일부 IDE 는 `NoInfer` 를 못 뚫고 헛경고를 낸다.
