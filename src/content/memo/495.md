![useTransition 으로 감싼 상태 갱신은 급하지 않은 것으로 처리돼, 타이핑 같은 급한 갱신이 먼저 되고 그동안 기존 화면을 유지하며 isPending 으로 진행을 알린다. await 뒤의 set 은 transition 에 안 잡혀 한 번 더 startTransition 으로 감싼다. useOptimistic 은 Action 이 진행 중일 때만 낙관적 값을 보여 주고 끝나면 원래 items 로 돌아간다 — 그래서 성공하면 items 를 갱신해야 남고, Action 밖에서 부르면 바로 되돌아간다. 그런데 React Query 가 캐싱·리페치·devtools·stale-while-revalidate·onMutate 롤백까지 이미 해 줘서, 쓰고 있다면 굳이일 때가 많다. useTransition 이 값을 하는 곳은 무거운 클라이언트 연산과 Server Actions 조합이다.](/svg/transition_optimistic_vs_query.svg)

```haskell
-- useTransition: 감싼 갱신은 급하지 않다 — 급한 것(타이핑) 먼저, 기존 화면 유지, isPending
handleFilter v = startTransition $ do
  d <- fetchData v
  startTransition (setResults d)        -- await 뒤의 set 은 transition 으로 안 잡힌다 → 다시 감싼다

-- useOptimistic: 보이는 값은 Action 이 진행 중인가로 정해진다
shown :: ActionState -> [a] -> [a] -> [a]
shown Running   _     optimistic = optimistic   -- addOptimistic item 즉시 반영
shown Finished  items _          = items        -- 끝나면 items. 성공했다면 items 를 갱신해야 남는다
shown OutsideAction items _      = items        -- Action 밖에서 부르면 경고와 함께 바로 되돌아간다
-- 좋아요·장바구니 추가 같은 인터랙션에

-- 현실: React Query 가 이미 캐싱·리페치·devtools·stale-while-revalidate·onMutate 롤백까지
-- 쓰고 있다면 "굳이?" — useTransition 이 값을 하는 곳은 무거운 클라이언트 연산, Server Actions
formAction fd = startTransition (createItem fd >> refresh router)
```
