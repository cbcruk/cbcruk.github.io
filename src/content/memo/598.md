> **apple/container 는 "컨테이너 1개 = 경량 VM 1개" 다.**

Docker Desktop 은 VM 하나를 띄우고 그 안에서 모든 컨테이너가 커널을 공유한다. apple/container 는 컨테이너마다 Virtualization.framework VM 을 띄우고 각 VM 이 **자기 커널로** 부팅한다. 아래가 전부 여기서 파생된다.

**언제** — 무언가를 설치·저장하기 **전에** 이 표를 본다. 셋 중 어디에 쓰느냐가 그것의 수명이다.

| 어디에 썼나 | `./esl stop/start` | `./esl rebuild` (컨테이너 재생성) | `container volume rm esl-home` |
|---|---|---|---|
| 이미지 안 (`Dockerfile`) | 유지 | **재빌드로 갱신** | 유지 |
| `/` 아무 곳 (`sudo apt install`, `/opt`, `/etc`) | 유지 | **소멸** | 유지 |
| `/home/dev/**` (코드·설정·캐시·SSH 키) | 유지 | 유지 | **소멸** |

**함정** — 컨테이너 안에서 `sudo apt install` 한 것은 `rootfs.ext4` 에만 있어서 `./esl rebuild` 하면 조용히 사라진다. 계속 쓸 툴은 `Dockerfile` 에 넣고, 홈에 들어가는 것(`uv tool install`·`pnpm add -g`)은 볼륨이라 살아남는다.

수치·경로는 전부 이 장비 실측이다 (container CLI 1.2.2, 2026-09-03).

# 구조

## Docker 와 무엇이 다른가

| | Docker Desktop | apple/container |
|---|---|---|
| 격리 단위 | 공유 VM 안의 namespace | 컨테이너별 독립 VM |
| 커널 | 전체가 1개 공유 | 컨테이너마다 1개 |
| 빈 컨테이너 기동 | 수십 ms | **0.56~0.62초** (VM 부팅, 3회 실측) |
| 네트워크 | 브리지 + 호스트 포트 매핑 | 컨테이너가 **자기 IP** (`192.168.64.x`) |
| 파일 저장 | overlayfs 레이어 | 컨테이너별 **ext4 블록 이미지** |
| 이미지·빌드 | BuildKit / OCI | **동일** (BuildKit, Dockerfile, Docker Hub) |
| Docker **API/소켓** | O | **X** — `docker.sock` 이 없다 |

```
$ ./esl run 'uname -a'
Linux esl-dev 6.18.15 #1 SMP ... aarch64
```

이 커널은 호스트 macOS 커널도, 공유 VM 의 커널도 아니다. `kernels/vmlinux-6.18.15-186`(kata 배포 커널)이 컨테이너 디렉터리로 복사되어 `esl-dev` 전용으로 부팅된 것이다.

## 호스트 프로세스

데몬 하나가 다 하는 구조가 아니라 launchd 서비스 여럿 + **컨테이너마다 런타임 하나**다.

```
container (CLI, 1회성)
   │ XPC
   ▼
com.apple.container.apiserver ─────────── 전체 오케스트레이션
   ├── container-core-images ──────────── 이미지/OCI 콘텐츠 스토어
   ├── container-network-vmnet.default ── vmnet NAT (192.168.64.0/24)
   ├── machine-apiserver ──────────────── VM 라이프사이클
   └── container-runtime-linux.esl-dev ── 컨테이너 1개당 1개!
            ▼
      com.apple.Virtualization.VirtualMachine.xpc   ← 실제 VM
            ▼
      [VM] vminitd (init) → entrypoint.sh → gosu dev → sleep infinity (PID 1)
                                              └ sshd, zsh, vscode-server ...
```

**읽는 법** — 컨테이너를 하나 더 만들면 `container-runtime-linux.<이름>` 이 하나 더 생기고, `container system stop` 은 이 전부를 내린다. 이미지 빌드를 하면 `buildkit` 컨테이너(2 CPU / 2 GB)가 추가로 뜬다. `container exec` 는 CLI → apiserver → runtime → `vminitd` → 게스트 fork 로 전달되므로 **exec 문제는 `vminitd.log` 에 다 남는다.**

## 디스크

전부 `~/Library/Application Support/com.apple.container/`(= `appRoot`) 아래다.

```
appRoot/
├── state.json          # 이미지 이름 → digest 인덱스
├── content/            # OCI 블롭 (pull 원본 레이어). 718 MB
├── snapshots/<sha>/    # 레이어를 푼 ext4 = 읽기전용 루트. 11 GB
├── kernels/            # 게스트 커널 바이너리. 15 MB
├── containers/esl-dev/
│   ├── config.json                 # 사용자가 준 스펙
│   ├── runtime-configuration.json  # VM 부팅 스펙으로 확정한 것
│   ├── kernel.bin · initfs.ext4    # 이 컨테이너가 부팅할 커널 / vminitd 루트
│   ├── rootfs.ext4                 # ★ 쓰기 가능한 루트 = /dev/vdb
│   ├── vminitd.log                 # 게스트 init (exec 추적)
│   └── stdio.log                   # PID 1 의 stdout/stderr
├── volumes/esl-home/volume.img     # ★ /home/dev = /dev/vdc
├── networks/default/               # vmnet NAT 정의
└── plugin-state/
```

VM 이 보는 블록 디바이스가 네 층이다:

| 층 | 호스트 파일 | 게스트 | 성격 |
|---|---|---|---|
| init | `containers/esl-dev/initfs.ext4` | `/` (초기) | vminitd 부팅용 |
| 이미지 | `snapshots/<sha>/snapshot` | 읽기전용 `/` | `esl-dev:latest` 레이어 |
| 쓰기 루트 | `containers/esl-dev/rootfs.ext4` | `/dev/vdb` → `/` | **컨테이너 삭제 시 소멸** |
| 홈 볼륨 | `volumes/esl-home/volume.img` | `/dev/vdc` → `/home/dev` | **영속** |

```
$ ./esl run 'df -h / /home/dev'
/dev/vdb   504G  6.0G  498G   2%  /
/dev/vdc    63G   14G   49G  23%  /home/dev
```

## 네트워크

```
macOS 호스트 ── vmnet NAT (192.168.64.1) ── esl-dev (192.168.64.2/24, MTU 1280)
```

컨테이너가 자기 IP 를 가지므로 호스트에서 `192.168.64.2:포트` 로 바로 붙는다 — `-p` 로 뚫어야만 접근되는 구조가 아니고, `esl` 의 SSH 접속이 이 방식이다. 게스트 DNS 는 `192.168.64.1`(호스트가 리졸버)이고 `/etc/resolv.conf` 에 그 한 줄뿐이다.

**IP 는 컨테이너를 재생성할 때마다 바뀐다.** 그래서 `esl` 이 `~/.ssh/config` 의 관리 블록을 매번 갱신하고 `HostKeyAlias esl-dev` 로 호스트 키 경고를 막는다(`R5` 가 이 추적을 없애는 길). MTU 1280 이 기본값이라, VPN·사내망과 겹칠 때 대용량 전송이 멈추면 여기를 의심한다.

## esl 셋업의 매핑

| 이 레포의 것 | apple/container 개념 | 실체 |
|---|---|---|
| `Dockerfile` | 이미지 `esl-dev:latest` | `content/` + `snapshots/` |
| `entrypoint.sh` | initProcess (root) → `gosu dev` | PID 1 = `sleep infinity` |
| `skel/` | 이미지에 구운 dotfile | 볼륨 최초 1회 시딩 (`~/.dev-seeded`) |
| `esl-home` 볼륨 | named volume, ext4 64G | `volume.img` → `/dev/vdc` |
| `esl` 스크립트 | CLI 래퍼 | `container run/exec/volume` + `~/.ssh/config` 관리 |
| `esl snapshot` | **볼륨 복사** (VM 스냅샷 아님) | `esl-snap-<이름>` 볼륨 |
| sshd (이미지 내장) | 컨테이너 IP:22 | Remote-SSH 진입점 |

`config.json` 실측: `cpus 4`, `memory 8 GiB`, `mounts: esl-home → /home/dev`, `publishedPorts: []`, `rosetta: false`, `ssh: false`. **호스트 마운트가 하나도 없다** — 격리 설계 그대로다.

## Docker 를 대체하나

> **기능은 대체한다. Docker "API" 는 대체하지 않는다.**

OCI 구현체이고 빌더가 BuildKit 그 자체라 `build/run/exec/pull/push/save/load/cp/logs/stats/inspect/prune`·`volume`·`network` 가 같은 이름으로 다 있고 옵션명도 대체로 같다. `Dockerfile` 문법도 그대로고 `ubuntu:24.04` 도 실제로 `docker.io/library/ubuntu` 에서 받아온 것이다.

안 되는 건 하나다 — `/var/run/docker.sock` 을 만들지 않고 Docker REST API 를 말하지 않는다. **소켓을 전제로 컨테이너를 조종하는 도구 전부**가 붙지 못한다.

| 못 쓰는 것 | 대안 |
|---|---|
| `docker compose` | 개별 `run` + 컨테이너별 IP, 또는 `container k8s`(실험적) |
| VS Code `Dev Containers` | **Remote-SSH** (이 셋업이 sshd 를 굽는 이유) |
| testcontainers | Docker Desktop 병행, 또는 테스트를 컨테이너 안에서 |
| `act`·Telepresence·docker context 쓰는 CI 툴 | Docker Desktop 병행 |

**`Dockerfile` 은 필수다.** `esl-dev:latest` 의 유일한 정의라 없으면 `./esl rebuild` 가 불가능하고, 격리 설계상 **호스트에 남기는 건 이 빌드 정의뿐**이다(개인 데이터는 볼륨에 있다). 평소 실행에는 안 읽으니 없어도 되는 것처럼 보이지만, rebuild 시점에 필요하다. 파일명은 자유고(`--file <경로>` 가 `Containerfile` 도 받는다, 실측) `esl` 이 경로를 명시하므로 바꾸면 스크립트도 고쳐야 한다.

**빌드 컨텍스트 제외는 `.dockerignore` 다 — `.containerignore` 는 무시된다.** 실측:

```
.containerignore ('*.md') → 컨텍스트 61.14 kB, *.md 전부 전달됨
.dockerignore    ('*.md') → 컨텍스트 19.45 kB, 제외 정상 동작
```

**메모리는 호스트에서 실제로 예약된다.** 8 GB 컨테이너를 켜 두면 그만큼 호스트가 빠지고, 컨테이너를 열 개 띄우는 compose 스택 스타일에는 불리하다. 대신 격리가 namespace 가 아니라 VM 경계다.

이 장비엔 Docker Desktop 도 깔려 있다(`/usr/local/bin/docker`, compose v5.3.0, 데몬 미실행). 그래서 판단이 필요하다 — **개인 작업은 `esl-dev` 안에서** 한다. Docker 쪽으로 옮기면 이미지·볼륨·빌드 캐시가 `~/Library/Containers/com.docker.docker` 에 남아 경계 밖으로 나간다. 반대 방향도 같다: **회사 작업을 `esl-dev` 안에서 하지 않는다**(회사 자격증명이 개인 볼륨에 섞인다).

# 레시피

## R1. 지금 상태 보기

```sh
./esl status                  # 컨테이너 + 볼륨 + IP
container ls -a               # 전체 컨테이너 (buildkit 포함)
container system status       # 서비스 동작 여부 + appRoot 경로
container system df           # 디스크 사용/회수 가능량
container stats esl-dev       # 실시간 CPU/메모리
container inspect esl-dev     # 확정된 스펙 전체 (JSON)
```

`container inspect` 가 사실상 최종 근거다 — "왜 이 환경변수가 있지", "볼륨이 어디 붙었지"는 전부 여기 있다.

## R2. 도구를 영구히 추가하기

```sh
vi Dockerfile     # apt 목록 또는 별도 RUN 에 추가
./esl rebuild     # 이미지 재빌드 + 컨테이너 재생성 (홈 볼륨은 유지)
```

임시로만 필요하면 `sudo apt install` 도 되지만 rebuild 에 사라진다. 언어 런타임·CLI 툴은 되도록 홈 볼륨 안(`uv tool install`, `pnpm add -g`)에 넣는다.

## R3. 컨테이너만 새로 만들고 작업 파일은 지키기

```sh
./esl rebuild                    # 재빌드 + 재생성 + ssh config 갱신
./esl destroy && ./esl start     # 이미지 그대로 재생성만
```

`destroy` 는 `container rm` 이라 `rootfs.ext4` 를 버린다 → `/` 에 직접 설치한 건 소멸, `/home/dev` 는 유지. 재생성 후 IP 가 바뀌므로 `esl` 이 `~/.ssh/config` 를 자동 갱신한다(수동이면 `./esl ip`).

## R4. 디스크 회수하기

```sh
container image prune          # 참조 없는 이미지/레이어 (여기서 ~9 GB)
container prune                # ⚠️ 정지된 컨테이너 전부 — esl-dev 가 정지 중이면 같이 지워진다
container volume prune         # ⚠️ 참조 없는 볼륨 — esl-snap-* 도 지워진다
./esl run 'pnpm store prune; uv cache prune; npm cache clean --force'
```

홈 볼륨 내부는 캐시가 대부분이다(`.cache` 4.4 GB, `.local` 4.8 GB, `.vscode-server` 3.0 GB, `workspace` 1.5 GB).

**함정 — sparse 파일은 안에서 지워도 호스트 디스크가 줄지 않는다.** `rootfs.ext4` 는 겉보기 550 GB / 실제 8.3 GB, `volume.img` 는 64 GB / 실제 20 GB 다. 게스트 `df` 는 줄지만 호스트 실사용량은 그대로고, **`./esl restore` 로도 안 줄어든다**(기존 `volume.img` 에 다시 쓰므로 할당된 블록이 그대로). 실제로 압축하려면 볼륨 파일을 새로 만든다:

```sh
./esl run 'pnpm store prune; uv cache prune; npm cache clean --force'
./esl snapshot compact          # 실사용분만 새 볼륨으로 복사
./esl destroy                   # 볼륨 점유 해제
container volume rm esl-home
container volume create -s 64G esl-home
container run --rm -v esl-snap-compact:/src -v esl-home:/dst \
  --entrypoint /bin/bash esl-dev:latest -c \
  'tar -C /src --exclude=./lost+found -cf - . | tar -C /dst -xpf - && sync'
./esl start
container volume rm esl-snap-compact
```

**확인** — `esl-snap-compact` 는 `esl-home` 이 정상 동작하는 걸 본 **뒤에** 지운다. 루트만 줄이려면 `./esl rebuild`(`rootfs.ext4` 가 새로 만들어진다).

## R5. IP 추적 대신 DNS 이름 쓰기

```sh
sudo container system dns create test          # .test 도메인 등록
container system dns list
ssh dev@esl-dev.test                           # <hostname>.<도메인>
```

이러면 `~/.ssh/config` 의 `HostName` 을 고정할 수 있고 IP 갱신이 필요 없어진다.

**미검증** — 이 장비에서는 실행하지 않았다(sudo 로 시스템 리졸버를 건드린다). 이름은 `config.json` 의 `networks.options.hostname`(= `esl-dev`)을 따를 것으로 보이지만 등록 후 `ssh`/`ping` 으로 확인할 것. 회사 장비에 sudo 로 리졸버 설정을 넣는 것이므로 그게 괜찮은지부터 판단한다.

## R6. 컨테이너의 개발 서버를 호스트 브라우저로 열기

```sh
./esl run 'cd ~/workspace/myapp && pnpm dev --host 0.0.0.0'
open "http://$(./esl ip):5173"
```

- 서버가 `127.0.0.1` 에만 바인드하면 호스트에서 안 보인다 → `--host 0.0.0.0` 필수.
- `localhost` 로 쓰려면 Remote-SSH 의 자동 포트 포워딩이나 터널: `ssh -N -L 5173:localhost:5173 esl-dev`
- 고정하려면 `container run -p 5173:5173`. 단 `-p` 는 재생성이 필요하니 일회성이면 터널이 편하다.

## R7. 파일을 호스트 ↔ 컨테이너로 옮기기

```sh
container cp ./file.txt esl-dev:/home/dev/workspace/
container cp esl-dev:/home/dev/workspace/out.log ./
scp esl-dev:/home/dev/workspace/out.log ./      # SSH 기반
```

**함정 — `container cp` 는 파일을 root 소유로 떨어뜨린다**(실측: `-rw-r--r-- root root`). `dev` 로 수정·삭제가 안 되니 넣은 뒤 소유권을 넘긴다:

```sh
container exec esl-dev chown -R dev:dev /home/dev/workspace/file.txt
```

`scp` 는 `dev` 로 인증하므로 이 문제가 없다 — 가능하면 SSH 쪽을 쓴다.

**격리 원칙** — 컨테이너 → 호스트 방향은 개인 파일을 회사 장비 파일시스템에 꺼내는 것이다. 로그·빌드 산출물 같은 일시적인 것만 꺼내고 소스·자격증명은 볼륨 안에 둔다. 호스트 디렉터리를 `-v` 로 마운트하는 것도 이 설계에 반한다(그래서 마운트가 0개다).

## R8. 안 될 때 로그 보는 순서

```sh
container logs esl-dev                 # PID 1 의 stdout/stderr (= entrypoint)
container system logs                  # apiserver·플러그인 등 호스트 측
tail -f "$HOME/Library/Application Support/com.apple.container/containers/esl-dev/vminitd.log"
container --debug <명령>                # CLI 단계별 상세
```

| 증상 | 먼저 볼 곳 |
|---|---|
| `exec` 가 걸리거나 실패 | `vminitd.log` |
| 부팅 직후 죽음 / entrypoint 오류 | `container logs esl-dev`, `stdio.log` |
| SSH 접속 불가 | `./esl ip` → `~/.ssh/config` 블록 IP 일치 → `container logs` 의 `sshd listening` |
| 이미지 빌드 실패 | `container builder start` 후 재시도, `container system logs` |
| 명령 자체가 안 먹음 | `container system status` → `container system start` |
| `VZErrorDomain Code=2 / storage device attachment is invalid` | 그 볼륨이 **이미 실행 중 컨테이너에 붙어 있다** → `./esl stop` 후 재시도 |
| 넣은 파일을 수정·삭제 못함 | `container cp` 가 root 소유로 넣었다 → `chown` (`R7`) |

## R9. CPU/메모리 바꾸기

`--cpus`/`--memory` 는 **생성 시점에 고정**된다(`config.json` 에 박힌다). `esl` 스크립트의 두 군데(`ensure_up`, `rebuild`)를 고친 뒤 `./esl rebuild`.

기본값은 `container system property list` 에서 관리된다(`[container] cpus = 4, memory = 1gb`, `[build] cpus = 2, memory = 2048mb`). `esl` 은 명시 인자로 4 CPU / 8 GB 를 준다. VM 이라 메모리가 실제로 예약되므로 안 쓸 때 `./esl stop` 이 의미가 있다.

## R10. 스냅샷/복원이 실제로 하는 일

`esl snapshot` 은 VM 스냅샷이 아니라 **볼륨 통째 복사**다.

```sh
./esl snapshot before-upgrade   # esl-snap-* 볼륨 생성 후 tar 파이프 복사
./esl restore before-upgrade    # 확인 프롬프트 + pre-restore-* 안전망 자동 생성
./esl snapshots ; ./esl snapshot-rm before-upgrade
```

- 복사 중 컨테이너가 잠시 **정지**한다. 볼륨이 실행 중 컨테이너에 배타적으로 붙어 동시 마운트가 안 되기 때문이고, 덕분에 쓰기 중간 상태가 안 섞인다. 실측한 실패 메시지가 `R8` 표의 `VZErrorDomain Code=2` 다.
- 복사는 `--rm` 임시 컨테이너로 `/src → /dst` tar 다.
- **소요 시간은 홈 크기에 비례한다.** README 의 "40 MB 기준 7초"는 초기값이고 지금 홈은 14 GB 라 수 분이다. `R4` 로 캐시를 먼저 정리하면 크게 짧아진다.

## R11. 완전히 지우기 (개인 데이터 잔여물 없이)

```sh
./esl destroy                       # 컨테이너만 (볼륨 유지)
container volume rm esl-home        # ★ 개인 데이터 실제 삭제
container volume ls                 # esl-snap-* 확인 후 개별 삭제
container image rm esl-dev:latest && container image prune
rm -f ~/.ssh/esl-dev_ed25519{,.pub} # 호스트에 남는 유일한 개인 자산
# ~/.ssh/config 의 '# >>> esl-dev BEGIN >>>' ~ '# <<< esl-dev END <<<' 블록 삭제
container system stop               # 서비스 내리기 (선택)
```

`volume.img` 가 파일 하나이므로 볼륨 삭제로 개인 데이터가 통째로 사라진다 — 이게 이 격리 구조의 이점이다.

## R12. 두 번째 격리 환경 만들기

VM 단위라 서로 완전히 독립이다. 단 **상단 변수 4개만 바꾸면 안 된다** — `esl-dev` 가 하드코딩된 자리가 더 있다(실측).

| 위치 | 놓치면 |
|---|---|
| L5~9 `NAME/IMAGE/VOLUME/SSH_ALIAS/SSH_KEY` | — (여기만 고치면 아래가 충돌) |
| L39 `begin/end` 마커 | 두 환경이 **같은 ssh config 블록을 덮어써서** 한쪽이 접속 불가 |
| L42/45/47 `Host`/`IdentityFile`/`HostKeyAlias` | 별칭·키가 첫 환경을 가리킴 |
| L64 로그 문자열 | 표시만 틀림 |
| L108 `SNAP_PREFIX` | 스냅샷 목록이 **두 환경에서 섞여 보임** |

`Dockerfile` 은 공유해도 된다(`IMAGE` 태그만 다르게). 런타임 서비스와 VM 이 추가로 뜨고 메모리는 각각 예약되니 동시 실행 시 호스트 여유를 감안한다.

# 검증 (2026-09-03)

버전은 container CLI·apiserver 1.2.2, buildkit 0.13.1, vminit 0.40.1, 게스트 커널은 kata-static 3.28.0 의 6.18.15 다. appRoot 총 사용은 46 GB 고 그중 약 15 GB 가 회수 가능하다. 나머지 수치는 위 본문에 그 자리에서 적어 뒀다.

**실측한 것**: 프로세스·launchd 서비스 목록, appRoot 구조와 용량, 게스트 커널·블록 디바이스·DNS, 기동 시간, `Dockerfile`/`Containerfile` 빌드, `.dockerignore` vs `.containerignore` 컨텍스트 전송량, 호스트 bind mount, 볼륨 배타 마운트 실패, `container cp` 양방향과 소유권, Docker Desktop 설치·데몬 상태.

**실측하지 않은 것**: `container system dns create`(sudo 필요 — `R5` 에 표시), `container k8s`(실험적), `container prune` 이 정지된 `esl-dev` 를 지우는 동작(파괴적이라 미실행 — `--help` 문구가 근거), Docker 와의 마운트 성능 비교, `R4` 의 볼륨 재생성 압축 절차(실제 데이터로 미실행).
